The Trading Floor

How the backend works

A social platform for day traders, where every post is a real trade. One hosting provider, one backend, one scheduled job — and a database that does most of the deciding.

!

Google does not host this. Google appears only as a sign-in provider and as the owner of the YouTube API that clips come from. The site is hosted by Vercel; everything stateful is Supabase. Worth being exact about, since "Google Cloud" would describe a different system from the one actually running.

Why the database decides

The page is JavaScript on someone else's computer and can be edited in a console, so it is never the thing enforcing a rule. The client decides what to draw. The database decides what the client is allowed to see.

RuleWhere it is actually enforced
A private account's trades stay hiddencan_view() → RLS policy on posts
Following a private account needs approvalfollows_set_status trigger + policy
A hidden P/L reaches nobody but its authorposts_feed view returns null
Blocked people cannot see each otherposts_feed, both directions
Comments can be switched offpolicy on comments
Profanity in handles and badgesname_violation(), SECURITY DEFINER
Headline ranking and topic taggingnews_topics(), news_feed view

The pattern repeats: a view shapes what a row looks like to the person reading it, an RLS policy decides whether they get the row at all, and a trigger stops the client sending something it shouldn't.

What the client actually reads

The app almost never selects from a base table. It reads views that already carry the joins, the counts and the per-viewer filtering.

posts_feed

Posts, author, like and comment counts, blocked people removed, P/L masked when its author keeps it private.

news_feed

Headlines with topics, is_market, matches_me and rank_at — the ranking, computed per reader.

profiles_stats

Profile plus follower, following and pending-request counts.

clips_feed

Creator Shorts with their like, save and comment counts.

strategies_list

Strategies with author, follower count and fork count.

follow_requests

Pending follows addressed to you, and nobody else.

The one piece of server code

fetch-news is the only thing running server-side. Every fifteen minutes pg_cron calls it through pg_net, and it reads news_sources for what to pull, resolves each YouTube channel's real uploads playlist (the usual UC→UU shortcut is not reliable for every channel), keeps only Shorts for creators, parses publisher RSS for headlines, and upserts the lot. A trigger tags each row by topic as it lands.

The YouTube API key lives in Edge Function secrets and never reaches the client.

What is public on purpose

The Supabase key in data.js is the publishable key and is meant to be visible. It identifies the project, not the person. What any request may read or write is decided by the JWT that Auth issued and the policies on each table — never by holding that key.
